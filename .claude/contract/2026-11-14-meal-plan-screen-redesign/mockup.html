Try it

  • Tap a day chip to jump days — the dots under each chip show how many meals are planned (3 = full day).
  • Tap the circle on a meal to mark it eaten. One-way, like today's "Mark as eaten" — no second tap undo, matching MPP-12.
  • Drag a meal card left (or click-drag with the mouse) to reveal Replace, Move and Remove. Replace opens a sheet with recent picks + browse; Remove shows an Undo toast.
  • Tap the day summary for the daily macro breakdown. ⋯ opens the week actions bottom sheet.
  • Empty slots show + Add lunch in place, which deep-links to Recipes filtered to that meal (today's /?mealType=lunch).

First-run swipe hint

The first time someone opens the plan on a phone, the first meal card slides left to show the hidden actions, three times, with a 👆 and a tip bubble. The tip stays until they actually swipe a card. Then a flag is saved and it never shows again on that device. Tapping or switching days doesn't count.

Meal Plan: from a list of names to a plan you can act on

The current screen does its job: it stores the week. But it doesn't help you use it. On desktop the seven narrow columns cut every name to "Froze…" or "R…". On a phone you scroll through seven tall cards to reach today. The useful features (swapping days, macros, marking a meal eaten, templates) are hidden behind clicks on things that don't look clickable. These eight ideas keep every existing feature and modal and change how you get to them.

The ideas

Spec panel: the rules this design encodes (please red-line)

  • No new data needed for 1, 3, 4, 5, 6, 8. They only rearrange data the week endpoint already returns (mealsByType, eaten, extraChoices, totalProtein/Carbs/Fat).
  • Macro dots/chips reuse evaluateMacro + DAILY_MACRO_TARGETS and the four directional colours (blue under · amber near · green on · red over). kcal is not traffic-lit, consistent with macroTargets.js.
  • No calorie target anywhere on the plan. kcal is shown as a plain number (day, week, avg/day) with no ring, bar or colour. A target would depend on the person (men vs women, size, goal), which the app doesn't model.
  • Eaten tick is one-way, the same rule as MealEatenSection (MPP-12), and per-person (MPP-33). Ticking is only allowed for today and past days. Future days show no tick.
  • Remove is never one tap. Desktop: ⋯ → Remove. Mobile: swipe → Remove. Both show a 5 s Undo toast, and the delete request goes out after the toast closes.
  • Swap days keeps SwapDaysModal. Only the trigger changes, to a visible ⇄ button on each day header.
  • First-run swipe hint (mobile). Shown until the user completes a real swipe (≥ 70 px left). Then localStorage['fb.mealplan.swipeHintSeen']='1' is written and it never shows again. Only a swipe dismisses it: viewing, tapping or changing day doesn't. It's per device (a new phone sees it once). Reads and writes are wrapped in try/catch; if storage is blocked, the hint shows every session rather than breaking. Alternative if you want it once per account: a users preference column. Costs a migration. Respects prefers-reduced-motion (bubble only, no animation).
  • One meal per slot, as today. A filled slot offers Replace Breakfast/Lunch/Dinner (on hover and in the ⋯ menu), never "add another". Dropping a meal onto a filled slot swaps the two.
  • Drag-to-move (desktop) calls the existing move/swap logic for one entry. If there's no single-entry move endpoint, this becomes a new backend task; flagged as the only real API change.
  • Pip nudge copy uses the existing +3/day rule (consistency only, never variety).
  • Header pill, footer nav, colours and fonts are unchanged. This is a Meal Plan screen redesign, not a rebrand.
