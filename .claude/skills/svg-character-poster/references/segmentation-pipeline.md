# Segmentation Pipeline — Scope Note

**Structural (won't go stale):** the phase order (segment → split clothing → props → verify → style), the reasoning for why each tool is used where it is, the specific past-session failure this design fixes, and the verification discipline in Phase 4.

**Owned by the model/library (can drift with versions):** the exact HuggingFace model ID, its label set, the `transformers`/`torch` API calls, SAM's specific API. If a model gets deprecated or a better one appears, update the script and this file's model ID — the *phase design* around it doesn't need to change.

## Why this replaced v1's approach

v1 traced every boundary by hand: color-ratio classifiers, ray-casting from an origin point, then per-boundary OpenCV GrabCut calls with manually placed seed points. That worked fine for one class of boundary (figure silhouette against open, evenly-lit background) and failed repeatedly on another (skin vs. hair) — because a well-lit hair strand and skin can land on nearly identical color, and no per-pixel color rule can arbitrate that correctly no matter how it's tuned. Three separate "fixed it" rounds on a test character's hair/face boundary turned out wrong before the error (a hair shape drooping across the face) was actually caught — by a human looking at it, not by the process that produced it.

Research turned up that this is already a solved problem: pretrained semantic human-parsing models exist specifically for skin/hair/clothing segmentation, trained on large labeled datasets rather than a handful of manually-placed seed pixels. Confirmed directly in the session that designed this pipeline: `isjackwild/segformer-b0-finetuned-segments-skin-hair-clothing` correctly separated Skin/Hair/Clothing/Background on a test photo in one pass, with a correct hairline on both sides of the head — no seeding, no tuning, better than every hand-rolled attempt that came before it.

## Phase 1 — Segment (automated, one model pass)

Use `E:\Photoshop\Claude\Scripts\human_parse_segformer.py`:

```python
from human_parse_segformer import parse_classes, silhouette_mask, save_debug_overlay
from silhouette_boundary import largest_connected_component, trace_mask_boundary, dots_svg

masks = parse_classes('reference.jpg')
# -> {'Background': bool array, 'Skin': ..., 'Hair': ..., 'Clothing': ...}

save_debug_overlay('reference.jpg', masks, 'debug_overlay.png')  # fast first look

outline = silhouette_mask(masks)                    # union of Skin+Hair+Clothing
outline_path = trace_mask_boundary(outline)          # same tracer as v1's outer silhouette

skin = largest_connected_component(masks['Skin'], seed_xy=(sx, sy))
skin_path = trace_mask_boundary(skin)
# same for masks['Hair'], each with its own connected-component seed point
```

`largest_connected_component` and `trace_mask_boundary` already existed in `silhouette_boundary.py` from v1 — nothing new to build there, just feed them a better mask. This gives clean Skin, Hair, and outer-silhouette boundaries with no manual seed placement per boundary, no ray-casting, no color-ratio tuning.

## Phase 2 — Split "Clothing" into real garment pieces

The model's `Clothing` class is one blob covering everything that isn't skin, hair, or background — jacket, vest, pants, boots, gloves, a held prop's straps, all of it. That's fine for the outer silhouette but not fine for the house style, which wants separate flat-color shapes per garment piece.

This is where v1's color-based tools are actually the right fit, unlike on skin/hair: garment-to-garment contrast (navy jacket vs. black vest vs. tan leather strap) is much higher than the skin/hair case that caused all the trouble, because these are usually genuinely different colors, not the same color under different lighting. Use `segment_material_grabcut()` (seeded within the `Clothing` mask, e.g. a vest-colored patch as foreground, a jacket-colored patch as background) or plain color thresholding for these splits. Still verify each one per Phase 4 below — "higher contrast, so simpler tools are appropriate" is not the same as "guaranteed correct."

## Phase 3 — Props AND same-color limb/garment splitting (SAM)

A held weapon or prop isn't a body/clothing class, so the segformer model won't segment it. The standard tool for arbitrary-object segmentation from a single point (or a few points) is Meta's **Segment Anything Model (SAM)**.

**Status: installed and verified (2026-08-23) — `pip install git+https://github.com/facebookresearch/segment-anything.git`, checkpoint `sam_vit_b_01ec64.pth` (the smallest, ~375MB, at `E:\Photoshop\Claude\Scripts\checkpoints\`) via `E:\Photoshop\Claude\Scripts\sam_segment.py`.** Confirmed on a real reference (Leon S. Kennedy, a crossed-arms gun-holding pose) after the v2 pipeline had shipped a broken result: it correctly separated a forearm sleeve, glove, torso, shoulder pad, gun, belt, holster, and both pant legs — all the same near-black navy fabric a color-based splitter (GrabCut/k-means) genuinely cannot tell apart, because SAM keys off learned edge/depth cues, not color.

**This is also the fix for same-color limb-vs-torso splitting, not just props.** The failure that motivated installing SAM wasn't (only) "no prop segmenter" — it was a session shipping one undifferentiated silhouette blob for an entire clothed body (torso+both arms+both legs, one `<path>`) because Phase 2's color-based garment split had failed on a uniform that's the same navy everywhere, and the fallback was hand-guessing coordinates off a printed grid instead of reaching for SAM. If Phase 2 fails for this reason (near-uniform garment color), use SAM per-limb (one click per arm/torso/leg segment, not one click for the whole clothing blob) before falling back to manual tracing.

### Practical usage — lessons from actually running it, not just the API

1. **A single foreground click is not enough near a seam.** Clicking on a forearm right next to the torso often returns "the whole shirt" or even "the whole person" as SAM's top-scoring candidate — the point alone doesn't disambiguate which coherent region you meant. Always add 1-4 **background-label points** (`point_labels=0`) on the neighboring regions you want excluded (e.g., a point on the chest to keep an arm click from bleeding into the torso).
2. **`argmax(scores)` is not reliable — SAM returns 3 candidates (roughly whole/part/subpart) and the highest-scoring one is frequently the wrong granularity**, sometimes even the near-full-canvas "background" interpretation. Always request `multimask_output=True`, render **all 3** as debug overlays, and pick by eye — the same look-before-trusting discipline as everything else in this pipeline, not a shortcut around it.
3. **Pick seed points from a gridded zoom-crop of the reference, not a guess.** A generic click 20-30px off target reliably lands on the wrong sub-object (this session's first pass got the shoulder strap, shoulder pad, and right-forearm clicks all landing on nearly the same wrong "neck/collar" region before re-cropping with a coordinate grid overlay fixed it). This is the same lesson `silhouette_boundary.py`'s docstring already states for boundary tracing — it applies equally to picking SAM's *input* points.
4. **Clean the returned mask before tracing it — but don't just keep "the largest component."** SAM's soft-edge threshold can leave a few disconnected stray pixels outside the main blob, which makes `trace_mask_boundary` start on a fleck instead of the real region (silently returning a near-empty 1-pixel "boundary"). The fix is `cv2.morphologyEx(mask, cv2.MORPH_CLOSE, ...)` then `cv2.connectedComponentsWithStats` — **but keeping only the single largest label is itself a bug**, confirmed on Leon's pants: the mask looked like one continuous two-legged blob in the debug overlay, but at the pixel level a strap crossing one thigh had split it into three real components (main right leg, a small upper sliver of the left leg, and the rest of the left leg) — "keep the biggest" silently discarded the entire left leg, and the loss was invisible on a photo-blended overlay because the real photo showed through the gap and looked fine. **Trace every component above a small noise-floor area (a few hundred px) and emit one path per component**, not just the single biggest one. A seed-flood-fill from the click point has the same problem from the other direction — it can miss real mask pixels if the exact click coordinate lands in a hole (a highlight, a lace gap).
5. **A per-shape SAM click gets you an accent/detail shape, not the whole garment.** Don't skip the outer silhouette. This session's first "fixed" rebuild still looked broken on a plain background (though it *overlaid the reference photo* looking fine) because only accent patches (a sleeve, a shoulder pad, a small vest strip) had been segmented — nothing filled the gaps between them (neck, sides, the jacket between the belt and the chest). Get one connected **base** shape too (e.g. the segformer `Clothing` mask restricted to the upper-body band, largest connected component) and layer the SAM accent shapes on top of it — same layering logic as v1's hand-drawn approach, just with real masks under it instead of guessed polygons.
6. **Verify by direct pixel-space compositing, not only by rendering the SVG file.** `cv2.fillPoly` each path's own coordinates directly onto a copy of the reference array and alpha-blend — this is more trustworthy for catching *coverage gaps* than eyeballing an SVG render, because a photo-blended overlay can visually hide an undrawn gap (the real photo shows through unfilled area and looks "fine" at a glance) in a way a plain-background render won't. Do both: a photo overlay for boundary *accuracy*, and a plain-white-background render for shape *coverage/gaps*.
7. If SAM still doesn't pan out for a specific small/thin shape (this session's shoulder strap — a thin, low-contrast diagonal band SAM kept merging into the collar), fall back to v1's manual Pen-Tool-style tracing for that one shape; that was never the part that was broken, and re-fishing for the right seed point past 2-3 tries costs more than a quick manual quad.
8. **Independently-traced adjacent shapes need to be grown a couple px before tracing, or their seams gap.** Two shapes that share a real-world boundary (a shoulder pad against the jacket, the belt against the pants, one leg's mask split by a strap into two components) were each traced from a *different* mask (different model, or a different connected component) — their simplified boundaries do not land on exactly the same pixels, so a thin sliver of background shows through at the seam on a plain background. This is invisible on a photo-blended verify overlay (the real photo shows through and looks fine) and only shows up on a plain-background render — which is exactly why Phase 4 requires both. Fix: `cv2.dilate()` every mask by ~2-3px before `trace_mask_boundary`, not after — z-order (later shapes drawn on top) absorbs the resulting slight overlap harmlessly, and the already-verified outward-facing edge of each shape is essentially unaffected.
9. **A manual fallback shape (point 7) gets silently lost if the SVG is later regenerated from the raw per-part script instead of edited in place.** This happened in practice: a hand-widened belt band (fixing a waist gap) was overwritten by a full script re-run that went back to SAM's narrow buckle-only belt mask, reopening the exact gap that had just been fixed. If a manual override shape is needed, either bake it into the generation script itself (not just the output SVG) or re-apply it explicitly as the last step after any regeneration — don't assume a re-run preserves hand edits.
10. **A click's mask can silently include a second, spatially separate patch of the same material elsewhere on the figure** — not just an adjacent region splitting into multiple components (point 4's pants case), but a genuinely distant, unconnected area that happens to share a color/texture class. Confirmed segmenting exposed skin on a gloved hand: a click meant for the fingers wrapping a gun grip also pulled in a patch of jaw/cheek skin tone elsewhere in the frame, and since that stray patch was pixel-wise larger, "keep the largest component" traced the wrong one (the face) instead of the fingers, with no error — just a boundary in the wrong place. Print the bbox of whatever component gets kept and sanity-check it's actually within the expected region for that body part before trusting it; add a background-exclusion point directly on the other same-toned area (the cheek/jaw, in this case) to stop the bleed at the source.
11. **A brighter/contrasting tone for a limb is only valid where the limb is a real, separate visible region in the photo — verify with the photo before adding it, not by assuming the anatomy must be there.** A crossed-arm or foreshortened pose can genuinely hide the bicep entirely behind the torso; forcing a "must have an arm shape here" click in that area finds whatever SAM can segment nearby (often collar or torso fabric) and produces a shape that reads as a stray blotch rather than a limb. Check the reference photo's actual silhouette at that location first — if there's no real separate region, don't invent one; let whatever *is* genuinely visible (a forearm guard, a glove, a shoulder pad) carry the "this is a limb" read instead.
12. **Fine repeated detail (finger separations, individual digits) is a legitimate, deliberate exception to the house style's minimal-detail default when it's specifically requested and the body part is a focal point (a hand gripping a prop).** This doesn't need its own SAM pass — a couple of thin same-hue-darker bands across the already-traced skin shape, placed by eye against a zoomed grid crop of the real crease lines, is enough. It's the same "second darker tone of the same hue, hard-edged, not a stroke/outline" technique `poster-conventions.md` already establishes for garment shading, just applied to skin.
13. **This whole pipeline (trace → `approxPolyDP` → straight `L` segments) defaults to a faceted, low-poly look — nothing in it ever produces a curve, and that's a real mismatch with the house style.** Confirmed by comparing a SAM-segmented rebuild directly against `leon-extracted.svg` (the real Photoshop vector-mask geometry for the same character, pulled from the actual poster PSD per the "Extracting" workflow below): every shape in the ground truth is authored as smooth cubic-bezier curves (`C` commands), never straight polygon edges — that's what makes a silhouette read as an organic body contour instead of a low-poly cutout. **Convert every shape's simplified vertex list to a smooth closed curve before writing the final `d` attribute — a Catmull-Rom → cubic-Bezier conversion, run on the same points `approxPolyDP` already produced, no re-tracing needed:**
    ```python
    def catmull_rom_to_bezier_path(points):
        n = len(points)
        d = f"M {points[0][0]},{points[0][1]} "
        for i in range(n):
            p0, p1, p2, p3 = points[(i-1)%n], points[i], points[(i+1)%n], points[(i+2)%n]
            b1 = (p1[0] + (p2[0]-p0[0])/6.0, p1[1] + (p2[1]-p0[1])/6.0)
            b2 = (p2[0] - (p3[0]-p1[0])/6.0, p2[1] - (p3[1]-p1[1])/6.0)
            d += f"C {b1[0]:.1f},{b1[1]:.1f} {b2[0]:.1f},{b2[1]:.1f} {p2[0]},{p2[1]} "
        return d + "Z"
    ```
    This is cheap enough to run as the very last step on an already-finished straight-line SVG (confirmed: reran it on a fully-built character and it introduced zero new gaps, verified with the same plain-background scan from Phase 4). But it belongs at the *end* of every shape's pipeline by default, not as an afterthought fix — every shape this pipeline produces should go through it before being called done, not just ones a reviewer happens to flag as "too angular."

    **Don't apply it to every shape indiscriminately — it badly overshoots on long, sparse-vertex, mostly-straight shapes.** Confirmed immediately after adopting this on the same character: the belt and holster straps (rigid gear, a handful of vertices spread along mostly-straight runs) turned into wavy, pinched, bulging blobs — the curve's tangent at each vertex is estimated from neighbor spacing, and a long straight run with widely-spaced points overshoots badly in a way a short, densely-sampled organic curve (a thigh, a boot) doesn't. The tell is a shape that now reads as "soft" or "stuck on" when the real object is rigid. **Only smooth genuinely organic body-silhouette shapes** (torso, limbs, boots, hair, face, a rounded armor plate) — leave straight-edged human-made gear (belts, straps, buckles, small rectangular detail patches, a weapon's hard lines) as straight `L` segments, the same way `leon-extracted.svg`'s own curves are tight/minimal on its rigid gear shapes and only pronounced on body contours. When in doubt, render both versions and compare against the reference photo — a rigid object that's ballooned into a blob is exactly as wrong as a body contour left faceted.
14. **A lower-opacity photo overlay (~40-50% drawn instead of ~70%) surfaces boundary errors the higher-opacity verify pass misses, because the real photo detail shows through more clearly for direct comparison.** Confirmed on the same character, on the user's suggestion: at 45% opacity, both pant legs showed a visible halo/gap sitting outside the real leg silhouette along their *entire* length — not a seam-specific issue, a uniform outward inflation of the whole shape. Root cause: the seam-closing dilation from point 8 (grow ~2-3px to close gaps against neighboring shapes) had been applied to the *entire* mask boundary, not just the edges that actually touch another shape — so edges facing open background got inflated too, with nothing to visually hide the excess (unlike a seam, where a neighboring shape's color would mask a small overshoot). Fix: erode the affected shape back down (rasterize → `cv2.erode` → re-trace → re-simplify → re-curve) rather than re-growing everything, and expect this to reopen a small gap at whatever seam actually needed the growth — patch that specific spot locally (and order it in the SVG so the neighboring shape draws on top, absorbing the patch's edges) rather than re-inflating the whole boundary again. **Don't treat every drawn shape that extends slightly past a real edge as automatically correct just because it "looks" fine at the usual verify opacity — do a low-opacity pass across the whole figure as a matter of course, not only when asked.**

## Phase 4 — Verify, with real discipline

This is the most important part of this document, more important than any of the tooling above. **A better segmentation model does not fix a shallow verification habit — it removes one source of error while leaving the other completely intact.** The session that designed this pipeline had a model-quality problem (fixed by switching to segformer/GrabCut) *and* a separate, more damaging self-verification problem (declaring a shape correct after a full-figure glance, three separate times, on a shape that was visibly wrong up close) that no amount of better tooling fixes by itself.

**When a low-opacity overlay shows an unexpected color/shape at a boundary, verify WHICH shape is actually wrong before fixing anything — the obvious suspect is often innocent.** A visible "wing" flaring past the waistline looked exactly like the torso-base shape overshooting (the same failure already seen and fixed on this character's belt and legs), so four separate rounds of curve-fitting fixes went into that shape — denser points, lower tension, then proper angle-based hard-corner detection — with **zero visible change in the render each time**. The real cause, found only by comparing the plain-flat render against a same-crop reference-photo-only image side by side: the torso-base shape was already correct: the real photo has black holster/strap gear sitting at that exact spot, and no shape had been drawn to cover it, so the (correctly-traced) base color showed through where black gear should have been. Fixing the actual holster/strap shapes (extending them to their real coverage) resolved it immediately; every round spent re-fitting the torso curve had been aimed at a shape that was never broken. **The tell that you're fixing the wrong shape: a targeted fix produces no visible change.** If a second attempt at the same fix also does nothing, stop and re-derive which shape is actually responsible — with a direct reference-vs-flat-render comparison at that exact crop, not another variation on the fix already tried twice.

**A quick hand-guessed rectangle to patch a missing-coverage gap is itself a common source of the next bug — it should still be measured against the reference, not eyeballed.** Immediately after the fix above (extending the holster/strap gear to cover a color gap), the quick rectangles used to do it were sized loosely and stuck out past the real body silhouette on both sides — a new, visible defect the user caught right away. The fix was the same discipline this whole document argues for everywhere else: get a real SAM segment of the region (one click + background exclusion, same as any other shape) instead of eyeballing a patch's corners, even for what looks like a small, low-stakes fix.

**The overlay/underlay eyeball checks below are what to use while drafting individual shapes. Before calling the WHOLE character done, run the exact pixel-diff + clip-path method instead — after several rounds of the user finding overflow/underflow that overlay checks (even a low-opacity one) either missed or mis-diagnosed, they said outright that any further overlay-based "looks tight" claim would be unacceptable.** This is not a stricter version of the same check — it removes eyeballing (and the misjudgment that comes with it) from the final call entirely, replacing "it looks right" with a number:
1. Get the reference photo's own ground-truth silhouette: `~segformer_masks['Background']`, cleaned to its largest connected component. This is independent of anything hand-drawn.
2. Render the flat SVG (plain background) and rasterize it to a silhouette (any non-background pixel = drawn).
3. `overflow = drawn & ~real`, `underflow = real & ~drawn`. Report both as **raw pixel counts**, not an impression — this is what actually answers "is it tight to the frame," not a look at a blended image.
4. **Wrap the whole character's `<g>` in an SVG `<clipPath>` traced from that same real silhouette** (dense `approxPolyDP`, ~0.0004–0.0006 of perimeter — too sparse and the clip's own simplification cuts into real silhouette territory, causing self-inflicted underflow). This makes overflow past the real photo edge **structurally impossible**, not just checked for — no individual shape's tracing/curve-fitting error can ever render past it, whatever it does.
5. With overflow now bounded by construction, fix remaining underflow with **generous full-region backing shapes per major color** (torso, legs, boots — each a plain oversized rectangle in that region's base color, drawn first/bottom), rather than chasing dozens of small individual gaps one at a time. The clip-path trims every backing rectangle to the true edge automatically, so there's no overflow risk in making them generous. Confirmed on this character: overflow went from 8516 px to 610 px, underflow from 1866 px to 915 px (both against a ~140,000 px figure, so both now comfortably under 1%, and what's left is 1-2px hairline — the resolution limit of the rasterization itself, not a real visible mismatch).

For every shape produced anywhere in Phases 1–3, before it is written into the character's SVG or described to the user as done:

1. Render it as a semi-transparent overlay directly on the reference photo (the live-browser or static-composite techniques from Core workflow step 5e-verify).
2. **Zoom into the actual boundary** — not the whole figure at arm's length. A full-figure render can look "basically right" while a specific edge is badly wrong; the wrong edge is exactly what a distant view hides.
3. **Describe in words what the zoomed crop actually shows**, specifically at the boundary — not "looks good," but naming the landmark it should align to (the jawline, the collar seam, the hairline crossing the temple) and confirming the shape's edge tracks it. If that description can't be written honestly, the shape isn't done.
4. **Also render the whole assembled SVG on a plain background (not blended with the reference photo) and check it for gaps between adjacent shapes — with an automated scan, not just eyeballing crops.** This is a distinct check from 1–3 and both are required — a photo-blended overlay can hide an undrawn seam between two independently-traced shapes (the real photo shows through the gap and looks fine at a glance), and a plain-background render can hide a boundary that's shifted a few px off the real edge (nothing to compare it against). Confirmed missing gaps this way in practice: a waist notch under the belt, a shoulder-pad/collar sliver, and — most seriously — an entire leg silently dropped by an over-aggressive "keep only the largest connected component" cleanup step, all invisible on the photo overlay alone.
   **Eyeballing zoomed crops one at a time is not reliable enough on its own** — a session doing exactly that judged a ~2-4px waist gap "negligible" and reported the figure gap-free, then the user found it immediately on the actual image. Run this instead: render on a plain white background, threshold near-white pixels, `cv2.connectedComponentsWithStats`, and flag any white component whose bounding box does **not** touch the canvas border — that's a hole fully enclosed by the figure, which is unambiguously a real gap no matter how small it looks. A component that does touch the border is just background. Zero non-border white components is the actual pass condition, not "looked fine at a glance."
4. Only after that description holds up does the shape get marked correct.

**When a shape sharing a boundary with another gets re-fixed, re-verify the neighbor too — don't assume it's fine because it was drawn earlier or by a different method.** This is not hypothetical: in the session that designed this pipeline, the face was rebuilt with GrabCut and re-checked repeatedly; the hair shape sitting right against it, drawn earlier by a worse method, was left unexamined on the assumption that "earlier and already reviewed once" meant "still correct" — and it was the one that was actually broken. Two shapes that share an edge are a joint problem. Fixing one side's technique without redoing the other side's verification leaves exactly this kind of mismatch.

## Phase 5 — Style pass (unchanged from v1)

Once every region's boundary is verified: flatten each to one flat color per material (sampled once from the real photo, reused everywhere that material appears across the whole character — never resampled shape by shape), decide which one or two detail shapes the character actually needs to read correctly (never automatic, never more than the silhouette needs), and apply the house style's shading/no-outline/no-facial-features rules from `poster-conventions.md`. This part of the pipeline was never the source of the session's problems and doesn't change.
